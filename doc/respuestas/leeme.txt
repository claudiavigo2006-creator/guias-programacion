1. Empleando void*en C o Objecten Java, pon un ejemplo de una estructura de datos, que empleando un array primitivo, permite alojar cualquier tipo de dato.
Respuesta
```java
public class ArrayGenerico {

    private Object[] datos;
    private int size;

    public ArrayGenerico(int capacidad) {
        datos = new Object[capacidad];
        size = 0;
    }

    public void add(Object obj) {
        datos[size] = obj;
        size++;
    }

    public Object get(int pos) {
        return datos[pos];
    }

    public static void main(String[] args) {

        ArrayGenerico arr = new ArrayGenerico(10);

        arr.add(5);
        arr.add(3.14);
        arr.add("Hola");

        System.out.println(arr.get(0));
        System.out.println(arr.get(1));
        System.out.println(arr.get(2));
    }
}
```

Este ejemplo emplea un array primitivo de tipo `Object[]`, lo que permite almacenar cualquier tipo de objeto en Java (`Integer`, `Double`, `String`, etc.), ya que todas las clases heredan de `Object`.

2. Brevemente, ¿Qué significa la programación genérica ? ¿Es el ejemplo anterior un ejemplo básico de programación genérica?
Respuesta
La programación genérica consiste en crear clases, estructuras de datos o métodos capaces de trabajar con distintos tipos de datos sin tener que reescribir el código para cada tipo concreto.

El objetivo es reutilizar código manteniendo seguridad de tipos.

El ejemplo anterior usando `Object[]` es un ejemplo básico de estructura de datos “genérica” en sentido informal, porque permite almacenar cualquier tipo de objeto. Sin embargo, no es programación genérica moderna real, ya que:

* pierde seguridad de tipos,
* requiere conversiones (*casting*),
* y los errores aparecen en tiempo de ejecución.

La programación genérica real en Java se hace usando genéricos (`<T>`), por ejemplo:

```java id="23kn90"
public class ArrayGenerico<T> {

    private T[] datos;
}
```

Con ello el compilador controla automáticamente los tipos y evita muchos errores.


3. Indica los problemas respecto al chequeo de tipos, de emplear void*o Objectcuando se crean estructuras de datos genéricos.
Respuesta
El principal problema de emplear `void*` en C o `Object` en Java para crear estructuras de datos genéricas es la pérdida de seguridad de tipos.

Los problemas principales son:

* El compilador no puede comprobar correctamente los tipos.
* Se necesitan conversiones manuales (*casting*).
* Los errores aparecen en tiempo de ejecución y no en compilación.
* Es fácil mezclar tipos incorrectos dentro de la misma estructura.
* El código es menos seguro y más difícil de mantener.

Por ejemplo, en Java:

```java id="u9t7ls"
Object obj = "Hola";

Integer n = (Integer) obj;
```

Compila correctamente, pero falla en ejecución con:

```java id="s3h2p8"
ClassCastException
```

Con genéricos (`<T>`), el compilador detectaría ese error antes de ejecutar el programa.

6. Sobre el funcionamiento de la programación genérica. ¿Qué hace el compilador cuando se instancia una clase que tiene parámetros de tipo? ¿Tienes lo mismo C++ y Java? ¿Qué es el "type erasure" de Java y la "instanciación de plantillas" de C++?
Respuesta
Cuando se instancia una clase genérica, el compilador adapta esa clase al tipo concreto indicado y comprueba que todos los usos sean correctos.

Por ejemplo:

```java id="7uknj7"
List<String> lista = new ArrayList<>();
```

el compilador verifica que solo se usen `String`.

Sin embargo, Java y C++ implementan esto de forma distinta.

### Java: type erasure

Java usa un mecanismo llamado **type erasure** (“borrado de tipos”).

Durante la compilación:

* el compilador comprueba los tipos genéricos,
* pero después elimina la información genérica.

Internamente, algo como:

```java id="vjlwm8"
List<String>
```

termina convirtiéndose aproximadamente en:

```java id="hlm8v0"
List<Object>
```

añadiendo automáticamente los *castings* necesarios.

Por eso en tiempo de ejecución Java no conoce realmente el tipo genérico exacto.

Ejemplo:

* `List<String>` y `List<Integer>` son la misma clase en runtime.

---

### C++: instanciación de plantillas

C++ funciona de forma diferente.

Cuando usamos:

```cpp id="rn3x42"
std::vector<std::string>
```

el compilador genera una versión real y específica del código para `std::string`.

Y si usamos:

```cpp id="dk7i3r"
std::vector<int>
```

genera otra versión distinta.

Esto se llama **instanciación de plantillas**.

Por tanto:

* en C++ sí existen versiones separadas para cada tipo,
* mientras que Java reutiliza una sola versión genérica mediante *type erasure*.

### Resumen

* **Java** → type erasure → los tipos genéricos desaparecen tras compilar.
* **C++** → instanciación de plantillas → el compilador genera código específico para cada tipo concreto.

7. Vamos a crear una nueva clase con parámetros de tipo. Defina en Java una clase Parque permita alojar dos valores de tipos diferentes. Incluye un constructor y un getter para cada tipo. Pon un ejemplo de uso de este Par, por ejemplo para especificar el tipo de retorno de una función que devuelve en un Parmedio y desviación típica de un array de double.
Respuesta
```java
public class Par<T, U> {

    private final T primero;
    private final U segundo;

    public Par(T primero, U segundo) {
        this.primero = primero;
        this.segundo = segundo;
    }

    public T getPrimero() {
        return primero;
    }

    public U getSegundo() {
        return segundo;
    }
}
```

Ejemplo de uso: una función que devuelve la media y la desviación típica de un array de `double`.

```java
public class Estadistica {

    public static Par<Double, Double>
            calcularMediaYDesviacion(double[] datos) {

        double suma = 0;

        for (double d : datos) {
            suma += d;
        }

        double media = suma / datos.length;

        double sumaCuadrados = 0;

        for (double d : datos) {
            sumaCuadrados += Math.pow(d - media, 2);
        }

        double desviacion =
                Math.sqrt(sumaCuadrados / datos.length);

        return new Par<>(media, desviacion);
    }
}
```

```java
public class Main {

    public static void main(String[] args) {

        double[] datos = {2, 4, 6, 8};

        Par<Double, Double> resultado =
                Estadistica.calcularMediaYDesviacion(datos);

        System.out.println(
                "Media: " + resultado.getPrimero()
        );

        System.out.println(
                "Desviación típica: "
                + resultado.getSegundo()
        );
    }
}
```

Aquí:

* `T` representa el primer tipo.
* `U` representa el segundo tipo.
* `Par<Double, Double>` indica que ambos valores son `Double`.

8. En Java, se pueden declarar parámetros de tipo también a nivel de método, no solo a nivel de clase. Pon un ejemplo con un método genérico seleccionaUno, que pasados ​​dos objetos del mismo tipo, te devuelva aleatoriamente uno de ellos. Muestra la diferencia de definirlo con dos Object, a definirlo con dos parámetros de tipo, en términos de (i) evitar downcasting y (ii) forzar que ambos objetos sean del mismo tipo.
Respuesta
### Versión usando `Object`

```java
import java.util.Random;

public class Utilidades {

    public static Object seleccionaUno(
            Object a,
            Object b) {

        Random rnd = new Random();

        if (rnd.nextBoolean()) {
            return a;
        }

        return b;
    }
}
```

Uso:

```java
String s = (String)
        Utilidades.seleccionaUno("Hola", "Adiós");
```

Problemas:

* Necesita *downcasting*.
* El compilador no obliga a que ambos objetos sean del mismo tipo.

Por ejemplo, esto compila:

```java
Object o =
    Utilidades.seleccionaUno("Hola", 5);
```

aunque mezcla tipos distintos.

---

### Versión usando método genérico

```java
import java.util.Random;

public class Utilidades {

    public static <T> T seleccionaUno(
            T a,
            T b) {

        Random rnd = new Random();

        if (rnd.nextBoolean()) {
            return a;
        }

        return b;
    }
}
```

Uso:

```java
String s =
    Utilidades.seleccionaUno("Hola", "Adiós");
```

Aquí:

* no hace falta *downcasting*,
* el compilador conoce el tipo real,
* y se obliga a que ambos parámetros sean compatibles.

Por ejemplo:

```java
Utilidades.seleccionaUno("Hola", 5);
```

produce error de compilación.

### Diferencias principales

#### (i) Evitar downcasting

Con `Object`:

```java
(String) ...
```

Con genéricos:

```java
String s = ...
```

el compilador infiere automáticamente el tipo.

#### (ii) Forzar mismo tipo

Con `Object` pueden mezclarse tipos distintos.

Con `<T>` ambos parámetros deben ser del mismo tipo (o compatibles), aumentando la seguridad de tipos.

9. ¿Se pueden establecer restricciones en los parámetros de tipo? Por ejemplo, si quiero definir un tipo genérico <T>, ¿puedo decir que tenga que ser, al menos, un número para poder tratarlo como tal? Pon un ejemplo en Java de un Puntocon dos coordenadas, métodos getX, getYy una función calcularDistanciaAotra Punto. Permite que esas coordenadas sean cualquier tipo de número. Pon dos soluciones: una simplemente creando coordenadas de tipo Numbery otra agregando genéricos para reforzar el chequeo de tipos y saber exactamente con qué tipo de número funciona el Punto. En este caso y respecto al "type erasure", ¿cuál es el tipo final tras la compilación?
Respuesta
Sí. En Java se pueden restringir parámetros de tipo usando `extends`.

Por ejemplo:

```java
<T extends Number>
```

significa que `T` debe ser `Number` o una subclase de `Number`, como `Integer`, `Double`, `Float`, etc.

## Solución 1: usando `Number`

```java
public class Punto {

    private final Number x;
    private final Number y;

    public Punto(Number x, Number y) {
        this.x = x;
        this.y = y;
    }

    public Number getX() {
        return x;
    }

    public Number getY() {
        return y;
    }

    public double calcularDistanciaA(Punto otro) {
        double dx = this.x.doubleValue() - otro.x.doubleValue();
        double dy = this.y.doubleValue() - otro.y.doubleValue();

        return Math.sqrt(dx * dx + dy * dy);
    }
}
```

Ejemplo:

```java
Punto p1 = new Punto(1, 2);
Punto p2 = new Punto(4.5, 6.7);

System.out.println(p1.calcularDistanciaA(p2));
```

Esta versión acepta cualquier `Number`, pero permite mezclar tipos distintos sin control.

---

## Solución 2: usando genéricos

```java
public class Punto<T extends Number> {

    private final T x;
    private final T y;

    public Punto(T x, T y) {
        this.x = x;
        this.y = y;
    }

    public T getX() {
        return x;
    }

    public T getY() {
        return y;
    }

    public double calcularDistanciaA(Punto<T> otro) {
        double dx = this.x.doubleValue() - otro.x.doubleValue();
        double dy = this.y.doubleValue() - otro.y.doubleValue();

        return Math.sqrt(dx * dx + dy * dy);
    }
}
```

Ejemplo:

```java
Punto<Integer> p1 = new Punto<>(1, 2);
Punto<Integer> p2 = new Punto<>(4, 6);

System.out.println(p1.calcularDistanciaA(p2));
```

También podríamos usar `Double`:

```java
Punto<Double> p3 = new Punto<>(1.5, 2.5);
Punto<Double> p4 = new Punto<>(4.5, 6.5);

System.out.println(p3.calcularDistanciaA(p4));
```

Pero ahora no se pueden mezclar fácilmente puntos de distinto tipo:

```java
Punto<Integer> pi = new Punto<>(1, 2);
Punto<Double> pd = new Punto<>(1.5, 2.5);

// Error de compilación
// pi.calcularDistanciaA(pd);
```

## Respecto al `type erasure`

En Java, después de compilar, el tipo genérico `T` se borra.

Como hemos escrito:

```java
<T extends Number>
```

el tipo final tras la compilación será aproximadamente `Number`.

Es decir, internamente quedaría parecido a:

```java
private final Number x;
private final Number y;
```

Por eso se dice que Java comprueba los genéricos en compilación, pero los borra en ejecución.

10. Sobre las soluciones anteriores. Si bien ambos permiten trabajar con distintos tipos de número sin duplicar la clase Punto, reflexiona sobre el refuerzo del chequeo de tipos con genéricos. ¿Permiten ambas crear un punto con una coordinada de tipo entero y la otra coordinada de tipo real? ¿Qué tipo devuelve el getXcon la solución sin generics y qué tipo devuelve el que tiene la solución con generics?
Respuesta
Sí, ambas soluciones permiten reutilizar la clase `Punto` para distintos tipos numéricos, pero la solución con genéricos refuerza mucho más el chequeo de tipos.

### Solución sin genéricos (`Number`)

Como las coordenadas son de tipo `Number`, se pueden mezclar tipos distintos:

```java
Punto p = new Punto(3, 4.5);
```

Aquí:

* `x` es un `Integer`
* `y` es un `Double`

El compilador lo permite porque ambos son subclases de `Number`.

Además, el método:

```java
getX()
```

devuelve:

```java
Number
```

Por tanto, si queremos tratar el valor como `Integer` o `Double`, necesitamos *casting* o usar métodos como:

```java
doubleValue()
```

---

### Solución con genéricos (`<T extends Number>`)

En esta versión:

```java
Punto<Integer> p = new Punto<>(3, 4);
```

las dos coordenadas deben ser del mismo tipo `T`.

Por eso esto no es válido:

```java
// Error
Punto<Integer> p =
    new Punto<>(3, 4.5);
```

porque:

* `3` es `Integer`
* `4.5` es `Double`

El genérico obliga a mantener coherencia de tipos.

Además, ahora:

```java

```

devuelve exactamente `T`.

Por ejemplo:

```java
Punto<Integer> p = new Punto<>(1, 2);

Integer x = p.getX();
```

sin necesidad de *casting*.

### Resumen

#### Sin genéricos (`Number`)

* Permite mezclar tipos numéricos.
* `getX()` devuelve `Number`.
* Menor seguridad de tipos.

#### Con genéricos (`<T extends Number>`)

* Obliga a usar el mismo tipo numérico.
* `getX()` devuelve exactamente `T`.
* Mayor seguridad y precisión de tipos.

Respuesta
Se puede resolver haciendo que la interfaz `Punto` sea genérica. Así, cada implementación indica contra qué tipo concreto de punto puede calcular distancias.

```java
public interface Punto<T extends Punto<T>> {

    double distanciaA(T p);
}
```

### Punto2D

```java
public class Punto2D implements Punto<Punto2D> {

    private final double x;
    private final double y;

    public Punto2D(double x, double y) {
        this.x = x;
        this.y = y;
    }

    @Override
    public double distanciaA(Punto2D p) {
        return Math.sqrt(
            Math.pow(this.x - p.x, 2) +
            Math.pow(this.y - p.y, 2)
        );
    }
}
```

### Punto3D

```java
public class Punto3D implements Punto<Punto3D> {

    private final double x;
    private final double y;
    private final double z;

    public Punto3D(double x, double y, double z) {
        this.x = x;
        this.y = y;
        this.z = z;
    }

    @Override
    public double distanciaA(Punto3D p) {
        return Math.sqrt(
            Math.pow(this.x - p.x, 2) +
            Math.pow(this.y - p.y, 2) +
            Math.pow(this.z - p.z, 2)
        );
    }
}
```

### Ejemplo de uso

```java
public class Main {

    public static void main(String[] args) {

        Punto2D p1 = new Punto2D(1, 2);
        Punto2D p2 = new Punto2D(4, 6);

        System.out.println(p1.distanciaA(p2));

        Punto3D p3 = new Punto3D(1, 2, 3);
        Punto3D p4 = new Punto3D(4, 6, 8);
```

Con esta solución ya no hace falta usar `instanceof` ni hacer *downcasting*, porque el compilador garantiza que:

* `Punto2D` solo calcula distancia con otro `Punto2D`.
* `Punto3D` solo calcula distancia con otro `Punto3D`.

La restricción:

```java
<T extends Punto<T>>
```

significa que `T` debe ser un tipo que también implemente `Punto<T>`. Esto refuerza la seguridad de tipos.


12. Dado que Stringes subtipo de Object, ¿significa eso que List<String>es subtipo de List<Object>? ¿Y cuál String[]es el subtipo de Object[]? Razona por qué la respuesta es diferente en cada caso y qué problema en el tiempo de ejecución puede aparecer con los arrays. A partir de estos ejemplos, defina qué significa que un tipo genérico sea covariante , contravariante o invariante respecto a su parámetro de tipo.
Respuesta
No. Aunque `String` sea subtipo de `Object`, eso no significa que `List<String>` sea subtipo de `List<Object>`.

En Java, los genéricos son **invariantes**.

```java
List<String> textos = new ArrayList<>();

// Error de compilación
// List<Object> objetos = textos;
```

Si Java lo permitiese, ocurriría este problema:

```java
List<String> textos = new ArrayList<>();

List<Object> objetos = textos; // Supongamos que esto fuese válido

objetos.add(5); // Añadimos un Integer

String s = textos.get(0); // Problema: esperábamos String
```

Por eso Java no lo permite.

En cambio, los arrays sí son **covariantes**:

```java
String[] textos = new String[3];

Object[] objetos = textos; // Esto sí compila
```

Pero puede fallar en tiempo de ejecución:

```java
objetos[0] = 5; // Error en ejecución: ArrayStoreException
```

Aunque la referencia sea `Object[]`, el array real sigue siendo un `String[]`, por lo que no puede guardar un `Integer`.

### Diferencia

* `List<String>` no es subtipo de `List<Object>`.
* `String[]` sí es subtipo de `Object[]`.

Los genéricos evitan el error en compilación.
Los arrays permiten la asignación, pero pueden fallar en ejecución.

### Variancia

Un tipo genérico es **covariante** si conserva la relación de herencia.

Si `String` es subtipo de `Object`, entonces:

```java
Tipo<String> sería subtipo de Tipo<Object>
```

Un tipo genérico es **contravariante** si invierte la relación de herencia.

Si `String` es subtipo de `Object`, entonces:

```java
Tipo<Object> sería subtipo de Tipo<String>
```

Un tipo genérico es **invariante** si no hay relación de subtipo entre los tipos genéricos.

Aunque `String` sea subtipo de `Object`:

```java
Tipo<String> no es subtipo de Tipo<Object>
```

En Java, `List<T>` es invariante respecto a `T`.

13. Java permite recuperar covarianza y contravarianza en tipos genéricos de forma controlada mediante comodines . ¿Qué es un comodín ( ?)? Muestra la diferencia entre List<? extends T>y List<? super T>, indicando en qué casos se usa cada uno. Pon dos ejemplos: (i) un método que recibe una lista de números y calcula su suma, usando ? extends; (ii) un método que recibe una lista y le añade varios números enteros, usando ? super.
Respuesta
Un comodín (`?`) en Java representa un tipo desconocido dentro de un genérico.

Permite trabajar con genéricos de forma más flexible, recuperando covarianza o contravarianza de manera controlada.

## `? extends T`

```java
List<? extends T>
```

significa:

* “lista de algún subtipo de `T`”.

Se usa cuando queremos **leer** datos de la lista, pero no modificarla.

Es covariante.

Ejemplo: sumar números.

```java
import java.util.List;

public class Utilidades {

    public static double sumar(
            List<? extends Number> lista) {

        double suma = 0;

        for (Number n : lista) {
            suma += n.doubleValue();
        }

        return suma;
    }
}
```

Uso:

```java
List<Integer> enteros = List.of(1, 2, 3);

List<Double> reales = List.of(1.5, 2.5);

System.out.println(sumar(enteros));
System.out.println(sumar(reales));
```

Aquí podemos leer elementos como `Number`.

Sin embargo, no podemos añadir elementos:

```java
// Error
// lista.add(5);
```

porque Java no sabe exactamente qué subtipo concreto contiene la lista.

---

## `? super T`

```java
List<? super T>
```

significa:

* “lista de algún supertipo de `T`”.

Se usa cuando queremos **insertar** objetos.

Es contravariante.

Ejemplo: añadir enteros.

```java
import java.util.List;

public class Utilidades {

    public static void añadirEnteros(
            List<? super Integer> lista) {

        lista.add(1);
        lista.add(2);
        lista.add(3);
    }
}
```

Uso:

```java
List<Number> numeros = new ArrayList<>();

añadirEnteros(numeros);

System.out.println(numeros);
```

Aquí podemos añadir `Integer` porque la lista acepta `Integer` o algún supertipo suyo (`Number`, `Object`, etc.).

Sin embargo, al leer:

```java
Object o = lista.get(0);
```

solo sabemos que devuelve `Object`.

---

## Resumen

### `? extends T`

* Covarianza.
* Se usa para leer.
* “Producer”.

### `? super T`

* Contravarianza.
* Se usa para escribir.
* “Consumer”.

Regla clásica:

> PECS
> Producer Extends, Consumer Super.
